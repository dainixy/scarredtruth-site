HIGH

🔒 Security — Supabase PII tables (results/messages/events) have Row-Level Security disabled

Your database tables holding women's answers, emails, and chat have no row-level protection on — they rely entirely on one server key staying secret, with no second line of defense.

Evidence & fix

Evidence: supabase-schema.sql creates results/messages/events via raw SQL with NO `enable row level security` and no policies. Supabase doesn't auto-enable RLS for SQL-created tables and the public `anon` role keeps default grants, so if the project's anon key (semi-public by design; the project URL is already known) is ever obtained, the whole PII table is readable via the REST API. The app uses the SERVICE key server-side (store-supabase.js), which bypasses RLS — so enabling RLS won't break it. Client ships no Supabase key (verified). The gap is missing defense-in-depth.

Fix: Enable RLS on all three tables with NO anon/authenticated policies (service role bypasses RLS, app keeps working). Verify with the anon key that the tables return zero rows.
